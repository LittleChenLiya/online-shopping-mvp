### 1. 验收范围与前置条件

- 范围限定为固定单一卖家、买家免注册、线上提交购买意向、线下付款与交货。注册、购物车、在线支付、多卖家、配送不列入本次验收。
- 记录待验收的 Git 提交号、运行环境、执行日期与执行人。按仓库启动说明启动同一版本的完整系统，前后端须连接实际接口。
- 使用独立测试数据库和虚构买家信息。准备一张符合格式的商品图片、有效商品信息及至少两位测试买家的意向。
- 使用卖家已登录和游客未登录的独立浏览器会话，分别验证页面行为与接口权限。所有会改变业务状态的限制均应由后端执行，不能仅以按钮隐藏或禁用作为通过证据。

### 2. 功能验收明细

下表“通过条件”中的各项均须满足。T01～T10 对应《测试用例与运行说明》的编号；涉及页面表现的项目，还须结合 T12 的浏览器验证。

| 需求 / 用例 | 验收场景与操作 | 通过条件 | 主要负责模块 |
|---|---|---|---|
| F01 / T01 商品浏览 | 分别在无商品、在售、冻结、已售状态下，以游客身份访问首页 | 无商品时显示明确空状态。在售时完整显示名称、描述、图片和价格。冻结时商品仍可见但不能提交购买意向。成交后首页不再展示该商品为当前可购买商品。 | 02，01 配合展示 |
| F02 / T02 购买意向 | 游客提交有效信息、缺少姓名或电话的信息、无效电话及空备注，并在冻结或下架后再提交 | 无需注册或登录。有效姓名和电话必填，备注可空。有效提交保存成功并给出反馈，卖家能够查询到对应意向。非法输入不得写入。冻结或下架商品拒绝新意向。提交意向本身不冻结商品，也不表示已付款或成交。 | 02，01 配合表单 |
| F03 / T03 登录与退出 | 游客直接访问卖家后台接口，尝试错误与正确凭据登录，退出后复用原会话 | 未登录不得发布商品、查询卖家历史或买家意向、处理交易或改密码。错误凭据不产生有效登录会话。正确凭据可以进入后台。退出后原会话失效，不能继续调用受保护接口。 | 05，01 配合界面 |
| F04 / T04 发布商品 | 提交完整有效商品，分别缺少必填项、输入非正数价格或不符合约定的图片，并在已有在售或冻结商品时再次发布 | 名称、描述、图片、正数价格均必填。有效商品发布后可供买家浏览。非法输入拒绝且不新增记录。同一时刻在售与冻结商品合计最多一件，重复或并发发布也不能突破限制。只有上一件已售后才能发布下一件。 | 03，05 配合数据库约束 |
| F05 / T05 商品历史 | 完成一件商品的交易，查询卖家历史，再发布下一件 | 已售商品记录仍保留，可查发布时间和成交时间。新商品发布不覆盖旧记录。买家首页不再把已售商品作为当前商品展示。历史查询受卖家权限保护。 | 03，04 提供成交状态和时间 |
| F06 / T06 查看意向 | 卖家与游客分别查询同一商品的买家意向，检查公开商品响应 | 卖家可以查看买家姓名、电话、备注和意向状态。游客不能调用卖家意向查询接口。公开商品页面及接口不暴露买家姓名、电话、备注等私人信息。 | 04，02/05 配合 |
| F07 / T07 冻结商品 | 为在售商品选择该商品的有效买家意向并冻结，再尝试提交新意向；另尝试不存在或属于其他商品的意向 | 有效选择后商品变为冻结状态，并关联所选意向。无效或不属于该商品的意向不得触发冻结。冻结后页面禁止购买，后端也拒绝新意向。冻结商品仍占用唯一未售名额。 | 04，02/03 配合状态约束 |
| F08 / T08 交易成功 | 尝试在未冻结时直接记录成交；再为有两个意向的商品冻结其中一个并记录成功 | 未冻结时拒绝直接成交。冻结后记录成功使商品变为已售、买家首页下架，所选意向变为已成交、其他意向结束。记录成交时间，历史保留，允许发布下一件。重复成交不能造成重复或错误更新。 | 04，02/03 配合展示和历史 |
| F09 / T09 交易失败 | 冻结商品后记录失败，重新查看商品和已有意向，再提交一条新意向 | 商品恢复在售，解除本次交易对象的冻结关联。已有意向记录保留且可继续联系、重新选择，新买家可再次提交意向。恢复在售后仍占用唯一未售名额。 | 04，02 配合意向提交 |
| F10 / T10 修改密码 | 已登录时输入错误原密码，再用正确原密码修改，并复用修改前的会话尝试访问后台 | 错误原密码拒绝且不改变现有密码。正确修改后旧密码不能登录，新密码可以登录。修改前已建立的卖家会话均失效，必须重新登录。 | 05，01 配合界面 |

### 3. 系统集成与界面验收

- **完整交易路径：**实际完成“发布商品、浏览、提交意向、选择买家冻结、记录成功、查询历史、发布下一件”，页面显示与后端状态一致。
- **交易失败路径：**实际完成“冻结、记录失败、恢复在售、再次提交意向或重新选择买家”，既有记录不丢失。
- **接口与数据：**同源 `/api` 请求能正常联通，POST 使用 JSON，卖家认证使用会话 Cookie。价格以整数分返回，页面以元正确显示，例如 1990 分显示为 19.90 元。图片按约定使用 Data URL。
- **T11 前端检查：**`node --check "01_前端界面/app.js"` 退出码为 0。语法检查只作为基础检查，不能替代功能验收。
- **T12 界面交互：**切换页面后内容与入口一致，较早请求不能覆盖当前页面。有效图片上传后能预览。交易确认框选择取消不改变状态，确认后才执行操作。桌面与窄屏布局无影响操作的遮挡、截断或整页横向溢出；记录实际测试的浏览器版本及视口宽度，不据此宣称覆盖所有浏览器和设备。
- 商品名称长度、图片大小上限、密码长度等实现细节，按照已有接口约定和测试用例补充边界检查；不能只因代码当前这样实现，就把它自动视为新增的需求条款。

### 4. 首次阶段成果与判定规则

**阶段成果检查：**需求规格说明书明确 F01～F10 和范围边界；五个模块有明确负责人、源码或成果链接；有接口与启动说明；测试清单能够追溯到需求；报告明确已完成、未完成和后续安排。上述材料齐备可作为首次阶段成果，不等于系统功能全部通过。

**单项功能判定：**

- 通过：该需求的全部通过条件满足，且实际结果、受测版本和证据可复核。
- 不通过：已执行验证，但至少一项实际结果不符合通过条件，需登记缺陷与复测结果。
- 待验证：尚未执行，或证据不足。不得将“代码已上传”“有测试脚本”“演示过部分流程”直接填写为通过。

**完整基线功能验收通过条件：**F01～F10 全部通过，两条完整业务路径均通过，T11、T12 在记录的环境内通过，且没有未解决的、影响上述验收条件的缺陷。只完成部分时，明确通过项与未通过/待验证项；教师对首次阶段成果的评审意见由教师实际给出，小组不代填。
