# 成员四：交易与冻结管理后端

## 我的任务

`trades.py` 负责卖家查看购买意向、选择买家冻结商品，以及根据线下结果标记成交或恢复上线。接口要求成员 5 的卖家认证；读取成员 2 的 intents，更新成员 3 的 products。前端按钮和确认框由成员 1 提供。

## 关键函数和变量

| 名称 | 功能 |
|---|---|
| list_trades(request, data) | 查询当前商品、全部意向及交易过程；通过 JOIN 加入商品名称和买家姓名 |
| update_trade(request, data) | 验证身份和 action，在同一事务内完成合法状态转换、意向更新、过程记录 |
| product_id | 当前操作的商品主键 |
| intent_id | 本次交易的购买意向编号，必须属于该商品且处于 pending |
| selected_intent_id | 商品记录上保存的交易对象，冻结时设置，失败时清空 |
| action | 操作类型，仅允许 freeze/success/failure |
| ROUTES | 交易查询和交易操作的接口映射 |

## 状态转换

| 操作 | 前提 | 商品结果 | 意向结果 |
|---|---|---|---|
| freeze | 商品 active；选择该商品的 pending 意向 | frozen，并保存所选意向编号 | 所选意向 selected，其他仍 pending |
| failure | 商品 frozen，已经选定意向 | active，清空所选编号 | 所选意向恢复 pending，可重新联系 |
| success | 商品 frozen，已经选定意向 | sold，记录 sold_at | 所选 completed，同商品其他 closed |

每次操作都插入一条 trade_events。商品更新、意向更新和记录插入在同一写事务中，任一步失败就整体回滚。已售商品不能恢复或再次成交。

## 接口

- `GET /api/trades`：返回 product/intents/events，仅卖家可调用。
- `POST /api/trade`：传 product_id/action，freeze 时额外传 intent_id。success/failure 使用数据库里已选定的买家，不信任前端重新指定买家。
- 参数错误 400，未登录 401，商品不存在 404，状态或买家不符合条件 409。

## 老师可能问什么

**问：为什么必须先冻结再成交？**  
答：题目要求交易前冻结；这让其他买家不能继续提交，同时明确当前交易对象。后端拒绝 active 直接转 sold。

**问：冻结是不是删除商品？**  
答：不是，只改变状态。商品仍可展示，但不能提交意向；失败后可原样恢复。

**问：买家 A 成交，买家 B 的意向怎么处理？**  
答：A 变为 completed，B 等其他意向变为 closed；记录仍保留给卖家查看。

**问：交易失败为什么保留买家意向？**  
答：没有成交不意味着买家信息必须删除，恢复 pending 后卖家可以再次联系或选择其他买家。过程表保留失败记录。

**问：怎么防止选择别的商品的买家？**  
答：查询意向时同时匹配 id 和 product_id，再检查 pending 状态；仅凭意向编号不够。

**问：重复点击成交会怎样？**  
答：首次成功后状态变为 sold，下一次发现不是 frozen，返回 409，不重复修改或插入事件。

**问：商品更新成功但意向更新失败怎么办？**  
答：都在 `connection(write=True)` 中，异常会回滚整个事务，避免只更新一部分。

**问：系统怎么知道线下真的付款了？**  
答：系统依赖卖家在线下交易后确认结果，没有接入支付接口，这与基线的线下交易要求一致。

## 演示检查

两位买家提交意向；选择一位冻结；买家再提交应失败；失败后商品恢复；再次冻结并成交，检查商品下架、其他意向结束、过程记录完整。未经冻结直接成交应失败。
