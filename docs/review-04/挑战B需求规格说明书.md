# 挑战 B 需求规格说明书

版本：3.0；修订日期：2026-11-26；适用：在线购物系统第四次评审。

本说明书保留 **105 条需求**，共列出 **301 个编号验证步骤**。每条采用同一格式：**需求说明、准备条件、验证步骤、通过标准**。先完成公共准备，再按需求编号独立检查；页面上能操作的功能优先用页面验证，参数、权限和异常情况使用接口工具。

## 一、目标与范围

挑战 B 要解决两件事：一是客户能够收藏商品、使用购物车多选下单；二是订单按“客户下单、商家确认、备货完成、开始发货、交易完成”处理，客户和商家在规定阶段可以取消。

本轮复用已有客户注册、商品与库存、卖家后台。付款仍在线下进行。本轮不验收线上支付、物流公司接入、快递轨迹和售后申请。

| 角色 | 本轮可以做什么 |
|---|---|
| 客户甲、客户乙 | 管理自己的购物车和收藏；下单、查本人订单；发货前取消本人订单 |
| 卖家 | 查看客户和订单；确认、备货、发货、完成；完成前取消订单 |
| 游客 | 浏览公开商品；操作购物车、收藏和个人订单前须登录 |

### 订单状态和取消边界

| 页面状态 | 接口值 | 卖家下一步 | 客户能否取消 | 库存变化 |
|---|---|---|---|---|
| 客户下单 | placed | 商家确认或取消 | 能 | 成功下单立即预留，不扣实物库存 |
| 商家确认 | confirmed | 备货完成或取消 | 能 | 保持预留 |
| 备货完成 | ready | 开始发货或取消 | 能 | 保持预留 |
| 开始发货 | shipped | 交易完成或取消 | 不能 | 扣实物库存，不再计本单预留 |
| 交易完成 | completed | 无 | 不能 | 不重复扣库存 |
| 已取消 | cancelled | 无 | 不能重复取消 | 发货前释放预留；发货后卖家取消则补回已发数量 |

一张订单可以有多种商品，所有明细使用同一个状态，取消也对整单生效。发货后取消按本版“整单作废并恢复库存”约定处理，实物是否退回由线下核实。

## 二、验证前先准备什么

### 2.1 启动独立测试环境

在**完整集成仓库根目录**打开 PowerShell。准备 JDK 17 或更高版本及 Maven，执行：

~~~powershell
. .\scripts\java-env.ps1
$reviewJava = Initialize-ShopJava
Invoke-ShopMaven -MavenArguments @('-f','backend-java/pom.xml','-DskipTests','package')
New-Item -ItemType Directory -Force -Path '.\data' | Out-Null
& $reviewJava -jar '.\backend-java\target\online-shopping.jar' --server.port=8003 --server.address=127.0.0.1 --shop.db-path='.\data\review-b-check.db' --shop.initial-password=seller12345
~~~

看到服务启动成功后，打开 http://127.0.0.1:8003/challenge-b 。保留此终端运行；测试“重启保留数据”时按 Ctrl+C 停止，再执行同一条 java 启动命令。

review-b-check.db 是本轮测试数据库。第一次验证选用新的测试库文件；如果该文件已有要保留的数据，改用另一个文件名。验证过程中重启必须继续使用同一个文件，不能换库后误判数据丢失。

### 2.2 账号和测试商品

1. 用 **Edge 普通窗口**注册并登录客户甲：用户名 reviewbuyer1，密码 Reviewb12345，电话 13800000000，默认地点“学校东门”。
2. 用 **Chrome 普通窗口**注册并登录客户乙：用户名 reviewbuyer2，密码 Reviewb12345，电话 13700000000，默认地点“图书馆”。
3. 用 **Edge InPrivate 窗口**登录卖家后台。新测试库初始卖家为 seller，密码为启动命令指定的 seller12345。
4. 卖家先创建一级分类“评审测试”、二级分类“测试商品”，再发布商品 A、B、C：名称分别为“评审陶杯”“评审陶碗”“评审托盘”；每种单价19.90元、库存5、上架，并上传一张测试图片、填写描述。
5. 从商品详情地址末尾记下各商品实际编号；甲乙从客户账号接口 GET /api/a/customer/account 的 customer.id 记下本人客户编号。

账号已存在时直接登录；要求“新客户、无历史订单”的条目应另注册新用户名，并在该条中把新账号视为甲。不要为了清空历史而删除团队已有订单。

**每条需求单独准备数据。**上一条若发货、取消或修改了数量，下一条须新建测试商品/订单，或先把数据恢复到该条“准备条件”。明确要求“无其他预留”时，要用没有被其他订单占用的新商品。

### 2.3 接口请求怎么发送

普通功能按页面步骤做。需要状态码或特殊参数时，用 Postman：

1. 请求地址填“http://127.0.0.1:8003 + 接口路径”。例如查询购物车填 http://127.0.0.1:8003/api/b/cart。
2. 方法选 GET 或 POST。POST 的 Body 选 raw、JSON；正文照条目填写。
3. POST 添加两个请求头：Content-Type: application/json、X-Requested-With: ShopApp。
4. 在对应账号浏览器的 F12 → Network 中，打开一次该账号的接口请求，查看 Cookie。甲乙请求只带各自的 shop_customer_session，卖家请求只带 shop_session。将相应值填入 Postman 的 Cookie 请求头。
5. 检查并关闭该请求的自动 Cookie 发送，避免 Postman 保存的其他会话覆盖手动 Cookie；游客测试须同时移除手动 Cookie。每次发送后记录状态码和 JSON 响应。

也可用各账号浏览器 Network 中的“复制为 cURL”导入 Postman，再修改路径或正文；须检查导入的账号身份、请求方法和 Body。

| 文中写法 | 实际操作 |
|---|---|
| {{A}}、{{B}}、{{C}} | 替换成测试商品真实数字编号，JSON中不加引号；也可设置同名Postman环境变量 |
| {{订单}} | 替换成该条创建的B订单编号，不是商品编号 |
| {{A意向}} | 替换成挑战A接口创建的意向订单编号，与B订单区分 |
| {{甲ID}}、{{甲订单}} | 分别替换为甲的客户编号、甲的B订单编号 |
| GET查询 | 查看响应；页面刷新只能验证显示，不能代替状态码检查 |
| 写操作返回200 | 只说明请求成功；还要按步骤再查询，确认实际数据 |
| 999999不存在 | 先核对测试库没有此编号；若已存在，改用另一个已确认不存在的正整数 |

常见响应：200成功，400参数错误，401未登录，403无权限或安全头错误，404不存在，409状态或库存冲突，413正文为空或过大，415正文类型错误。

### 2.4 查库存和推进订单的位置

- 查库存：卖家后台 → 商品与库存，查看“库存总量 / 预留 / 可用”；接口也可用 GET /api/a/seller/products?size=100，找到对应商品。
- 改库存：卖家后台 → 商品与库存，找到该商品，在“调整库存与上下架”中输入目标库存、勾选上架、点击“保存”。商品有其他预留时改用新商品，不强行覆盖占用。
- 准备购物车数量：车中没有该商品时，在商品详情输入目标数量后点击“加入购物车”；已有条目时，在购物车改数量并点“保存数量”，不要反复加购而误把数量累加。
- 查客户订单：客户“我的订单”，或 GET /api/b/orders。
- 查卖家订单：卖家后台 → 订单管理，或 GET /api/b/seller/orders。
- 从新订单准备“已确认”：卖家点一次“商家确认”。
- 准备“备货完成”：依次点“商家确认”“备货完成”。
- 准备“已发货”：再点“开始发货”；准备“已完成”：继续点“交易完成”。
- 每次点击后在确认框点“确认操作”，并刷新检查状态。每条使用自己的新订单，不把同一订单反复当作不同前置状态。

金额以整数分返回：1990表示19.90元。stock为实物库存，reserved为已被订单占用的预留数量，available为还能购买的数量；可用量=实物库存−预留。

## 三、逐条需求与验证步骤

以下“通过标准”必须全部满足才记为通过。步骤写的是待执行的验证方法，不是已完成的测试记录。

### 3.1 收藏商品（9条）

#### B-FAV-01 添加收藏

**需求说明：**登录客户可把存在的商品加入本人收藏，不改变库存。

**准备条件：**客户甲已登录；商品A在售，甲未收藏A。

**验证步骤：**

1. 甲打开商品A详情页，点击“收藏商品”。
2. 打开“收藏”页，找到商品A。
3. 刷新页面，再检查一次。

**通过标准：**两次查看都有且只有一条A，页面提示收藏成功。

#### B-FAV-02 收藏列表

**需求说明：**客户可查看本人的收藏，含商品当前名称、价格、状态、可用数量与图片。

**准备条件：**甲已收藏商品A。

**验证步骤：**

1. 打开“收藏”页，核对A的名称、价格和可用数量。
2. 用甲身份发送 GET /api/b/favorites。
3. 展开A的product，检查name、price_cents、status、available、images。

**通过标准：**页面与返回信息一致；价格以分返回，1990分在页面显示19.90元，图片列表非空。

#### B-FAV-03 收藏去重

**需求说明：**同一客户重复收藏同款只保留一条，重复请求不报错。

**准备条件：**客户甲已登录，收藏中没有A。

**验证步骤：**

1. 在A详情页连续点击“收藏商品”两次。
2. 打开收藏页并刷新。
3. 发送 GET /api/b/favorites，数出product_id等于A的条数。

**通过标准：**两次收藏均成功；A始终只有一条。

#### B-FAV-04 客户隔离

**需求说明：**甲的收藏不能被乙看到或移除。

**准备条件：**甲乙分别登录到独立浏览器，均已收藏A。

**验证步骤：**

1. 甲打开收藏页，确认有A。
2. 乙在自己的收藏页移除A。
3. 甲乙分别刷新收藏页。

**通过标准：**甲仍有A，乙没有A；乙的操作没有删除甲的数据。

#### B-FAV-05 移除收藏

**需求说明：**客户可移除本人指定收藏，不删除商品和购物车条目。

**准备条件：**甲已收藏A，并把A加入购物车2件。

**验证步骤：**

1. 甲在收藏页点击A所在行的“移除”。
2. 刷新收藏页，再打开购物车。
3. 卖家打开商品与库存页，查找A。

**通过标准：**收藏没有A；购物车仍有A两件；商品A仍存在。

#### B-FAV-06 重复移除

**需求说明：**不存在或已移除的收藏按幂等成功处理。

**准备条件：**甲已收藏A，记录A的实际商品编号。

**验证步骤：**

1. 甲发送 POST /api/b/favorites/{{A}}/remove，正文为 {}。
2. 原样再次发送同一请求。
3. 发送 GET /api/b/favorites。

**通过标准：**两次移除均为200；最终列表中没有A，不出现重复删除错误。

#### B-FAV-07 下架收藏

**需求说明：**下架商品继续保留收藏；允许按已知 ID 收藏仍存在的下架商品。

**准备条件：**A没有未发货预留；记录A编号；甲已收藏A。

**验证步骤：**

1. 卖家在商品与库存页取消A的“上架”勾选并保存。
2. 甲刷新收藏页，检查A仍在且显示下架。
3. 甲移除A，再发送 POST /api/b/favorites，正文 {"product_id":{{A}}}。

**通过标准：**原收藏不消失；重新收藏也返回200；GET收藏中A的product.status为off。

#### B-FAV-08 无效商品

**需求说明：**收藏编号须为正整数且商品存在。

**准备条件：**甲已登录；确认999999不是现有商品编号。

**验证步骤：**

1. 分别发送 POST /api/b/favorites，正文为 {"product_id":0}、{"product_id":"123"}、{"product_id":999999}。
2. 每次记录状态码。
3. 查询收藏，确认没有新增无效项。

**通过标准：**前两次为400，最后一次为404；收藏不新增任何无效商品。

#### B-FAV-09 空收藏

**需求说明：**没有收藏时返回空列表，页面显示空提示。

**准备条件：**甲已登录。

**验证步骤：**

1. 打开收藏页，逐条点击“移除”，直到全部清空。
2. 刷新收藏页。
3. 发送 GET /api/b/favorites。

**通过标准：**页面显示“暂时没有商品”；接口items为[]，不报错。

### 3.2 购物车（12条）

#### B-CART-01 选择加购

**需求说明：**登录客户可按商品编号及数量把未下架商品加入购物车。

**准备条件：**甲已登录，购物车没有A，A在售且库存5。

**验证步骤：**

1. 甲打开A详情，把购买数量填2。
2. 点击“加入购物车”，再打开购物车并刷新。
3. 发送 GET /api/b/cart 核对A所在项。

**通过标准：**购物车有A一行，quantity=2。

#### B-CART-02 同款合并

**需求说明：**同一客户同款只有一行；默认及 add 模式累加数量。

**准备条件：**甲的购物车没有A，A在售。

**验证步骤：**

1. 在A详情加购2件，再回到详情加购3件。
2. 刷新购物车，统计A的行数及数量。
3. 发送 GET /api/b/cart 再核对。

**通过标准：**A只有一行，quantity=5；不是两行。

#### B-CART-03 覆盖修改

**需求说明：**mode=set 将数量设置为请求值；原条目不存在时创建。

**准备条件：**甲购物车中A为5件，B不在购物车。

**验证步骤：**

1. 发送 POST /api/b/cart，正文 {"product_id":{{A}},"quantity":2,"mode":"set"}。
2. 再发送同接口，正文 {"product_id":{{B}},"quantity":3,"mode":"set"}。
3. 查询购物车。

**通过标准：**A改为2件；B新增3件；写响应均为200。

#### B-CART-04 数量范围

**需求说明：**单次数量及累加结果均须为 1～1000000，拒绝越界且不改原数据。

**准备条件：**甲购物车A为1件，A在售。

**验证步骤：**

1. 对 POST /api/b/cart 依次提交A及quantity为0、-1、1000001，每次用mode=set。
2. 查询确认A仍为1件；再用set把A设为1000000。
3. 以mode=add再加1件，随后查询。

**通过标准：**前三次400且原值不变；设置1000000成功；再加1为400，最终仍为1000000。

#### B-CART-05 数量类型

**需求说明：**quantity 必须为 JSON 整数，拒绝字符串、小数、布尔值、null 和缺失。

**准备条件：**甲购物车A为2件。

**验证步骤：**

1. 复制合法加购请求，分别把quantity改为字符串"2"、1.5、true、null；最后删除quantity字段。
2. 逐次发送 POST /api/b/cart 并记录状态码。
3. 查询A的最终数量。

**通过标准：**五种请求均为400；A仍为2件。

#### B-CART-06 模式约束

**需求说明：**mode 支持 add、set；省略或去除首尾空白后为空时累加；其他值拒绝。

**准备条件：**甲购物车A为1件。

**验证步骤：**

1. 发送加购A1件的请求，省略mode；再发送一次mode为空字符串的请求。
2. 查询购物车，确认A变为3件。
3. 再发送mode="delete"的加购请求并查询。

**通过标准：**前两次为200且累加到3；最后400，仍为3件。mode为add表示累加，set表示覆盖。

#### B-CART-07 移除条目

**需求说明：**按商品 ID 移除本人购物车条目；重复移除仍成功。

**准备条件：**甲乙的购物车都已有A。

**验证步骤：**

1. 甲在购物车找到A，点击该行“移除”。
2. 甲发送 POST /api/b/cart/{{A}}/remove，正文 {}，再移除一次。
3. 甲乙分别刷新购物车。

**通过标准：**甲没有A，乙仍有A；重复移除为200。

#### B-CART-08 读取购物车

**需求说明：**展示每项数量及商品当前单价、实物库存、预留、可用量和状态。

**准备条件：**甲已加购A两件，A价格19.90元、库存5、没有预留。

**验证步骤：**

1. 刷新甲购物车，查看A的价格、可用数量和购买数量。
2. 发送 GET /api/b/cart，找到A。
3. 核对quantity及product中的price_cents、stock、reserved、available、status。

**通过标准：**分别为2、1990、5、0、5、active；页面价格为19.90元。

#### B-CART-09 客户隔离

**需求说明：**购物车归属由会话决定，不接受请求体 customer_id 指定他人身份。

**准备条件：**甲购物车有A，乙购物车为空；已记录甲客户ID。

**验证步骤：**

1. 乙查询 GET /api/b/cart。
2. 乙发送 POST /api/b/cart，正文 {"product_id":{{A}},"quantity":1,"customer_id":{{甲ID}}}。
3. 甲乙分别查询购物车。

**通过标准：**乙首次查询无A；随后A只加到乙自己的车；甲的原数量不变。

#### B-CART-10 不占库存

**需求说明：**加购、改数量和移除不预留、不扣实物库存。

**准备条件：**A库存5、无任何预留，甲购物车没有A。

**验证步骤：**

1. 卖家记录A的实物库存5、预留0。
2. 甲加购A两件，再保存数量为3，最后移除A。
3. 卖家刷新库存页。

**通过标准：**全过程结束后实物库存仍为5、预留仍为0。

#### B-CART-11 下架与缺货边界

**需求说明：**不存在商品加购为 404，下架为 409；未下架时允许先存高于可用量的数量。

### 4.2 两个客户同时抢最后一件

用于 B-STOCK-07。使用前先发布新的商品A，库存1；确认没有其他预留。

1. 把下列代码复制到测试仓库中的临时文件 check_last_stock.py。

~~~python
import json
import uuid
from http.cookiejar import CookieJar
from urllib.request import build_opener, HTTPCookieProcessor, Request
from concurrent.futures import ThreadPoolExecutor
from threading import Barrier

BASE = 'http://127.0.0.1:8003'
PRODUCT_ID = 0  # 改为本条新商品A的真实编号
ACCOUNTS = [
    ('reviewbuyer1', 'Reviewb12345'),
    ('reviewbuyer2', 'Reviewb12345'),
]
if PRODUCT_ID <= 0:
    raise ValueError('请先填写新商品A的真实编号')

def post(client, path, data):
    request = Request(
        BASE + path,
        data=json.dumps(data).encode('utf-8'),
        headers={
            'Content-Type': 'application/json',
            'X-Requested-With': 'ShopApp',
        },
        method='POST',
    )
    with client.open(request, timeout=20) as response:
        return json.load(response)

clients = []
for username, password in ACCOUNTS:
    client = build_opener(HTTPCookieProcessor(CookieJar()))
    post(client, '/api/a/customer/login', {
        'username': username, 'password': password
    })
    post(client, '/api/b/cart', {
        'product_id': PRODUCT_ID, 'quantity': 1, 'mode': 'set'
    })
    clients.append(client)

gate = Barrier(2)
def checkout(client):
    gate.wait(timeout=10)
    return post(client, '/api/b/orders', {
        'product_ids': [PRODUCT_ID],
        'request_key': str(uuid.uuid4()),
    })

with ThreadPoolExecutor(max_workers=2) as pool:
    results = list(pool.map(checkout, clients))
for account, result in zip(ACCOUNTS, results):
    print(account[0], json.dumps(result, ensure_ascii=False))
assert sum(result.get('created') is True for result in results) == 1
~~~

## 五、接口速查

全部B写接口均为POST，正文为JSON对象；移除操作发送 {}，不能不发送正文。

| 方法与路径 | 必要参数 | 主要返回 |
|---|---|---|
| GET /api/b/cart | 客户Cookie | items：购物车列表，包含quantity和当前product |
| POST /api/b/cart | product_id、quantity；mode可选add或set | message；须再GET确认数量 |
| POST /api/b/cart/{id}/remove | 商品id；正文{} | message |
| GET /api/b/favorites | 客户Cookie | items：收藏列表 |
| POST /api/b/favorites | product_id | message |
| POST /api/b/favorites/{id}/remove | 商品id；正文{} | message |
| POST /api/b/cart/favorite | product_ids：1～100个唯一正整数 | message |
| POST /api/b/orders | product_ids；8～80字符request_key | created、rejected、message；成功时有order |
| GET /api/b/orders | page默认1，size默认20 | orders、total、page、page_size |
| POST /api/b/orders/{id} | 订单id；action=cancel | message、order |
| GET /api/b/seller/orders | page、size；customer_id可选 | orders、total、page、page_size |
| GET /api/b/seller/customers | 卖家Cookie | customers，含订单数及已完成金额 |
| POST /api/b/seller/orders/{id} | 订单id；action为confirm/ready/ship/complete/cancel | message、order |

补充约束：

- product_id、quantity、product_ids中的编号必须为JSON整数，不能传带引号数字；quantity及累加后的数量为1～1000000。
- mode省略或去掉首尾空白后为空，均按add累加；set覆盖原数量。
- page范围1～1000000，size范围1～100。商品编号与订单编号不是同一类编号。
- 部分缺货：created=true、订单只包含有货项，rejected列出缺货项；全部缺货：created=false，没有order字段。
- 成功创建后的同key、同商品集合返回原订单；仅更改数组顺序仍视为同一集合。全部缺货未建单的结果不保存在幂等订单记录中，重试会重新判断。
- 无独立 GET /api/b/orders/{id} 详情路由；完整明细随列表或成功操作返回。
- 移除路径由long类型绑定，不存在的数字商品编号按幂等成功；不能把JSON中product_id的正整数校验与移除路径混为一谈。
- 直接修改状态、库存的请求必须验证身份和前置状态，隐藏按钮不能代替服务端拒绝。
